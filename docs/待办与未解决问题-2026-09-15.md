**C2 —— 读图标签 OCR 不稳定：同一份代码、同一张图，两次读数就不同**

用**生产原文件（未改动）**对 59 张真实图跑两遍，**9 张结果不同**：

| 图 | 第 1 次 | 第 2 次 |
|---|---|---|
| `7685319584487951562_0.png` | sl=0.0 entry=0.04 tps=[88.0] | **「无红色止损标签」**（标签全丢） |
| `7685387377082125571_0.png` | sl=1066.72 entry=1094.53 tps=[1112.2, 1301.85] | sl=1094.53 entry=1112.2 tps=[1301.85] |
| `7685512071131172073_0.png` | tps=[77366.6, 79205.2, 80294.5] | tps=[77366.6, 78667.4, 79205.2] |

机制：`_ocr_tags_batch()` 把 N 个标签**拼成一张图 + 黄色序号**，让视觉模型返回
`{"1":v,"2":v,…}`，再用 `nums.get(str(i))` 把数值贴回第 i 个标签。
**模型一旦漏答/错位，"序号↔数值"就配错，或者整图标签全丢** → 止盈档位直接读错。

- 已做的最小兜底：返回条数 ≠ 标签数就**重试一次**并把"没读全"写进日志（不再静默丢标签）。
- **实测结论（不含糊）**：这只堵住"整图标签全丢"这一类，**数值错位仍在**——
  同一张 `7685512041913666779_0.png` 三次跑出三组不同止盈。
- **建议的下一步见 0.16.6，要你点头再动。**

### 0.1 B2 外部巡检（已实现并部署，**不依赖机器人进程、不重启机器人**）

**为什么不照原文档的方案做**：原方案是「每 5 分钟跑 health_check.py，输出含
`BrowserContext` 就告警」。实测**这样会永久告警**：health_check 扫的是 run.log 的
**最近 400 行**，而实测最近 2000 行里有 **694 条** `BrowserContext` / `页面不存在` /
`重开失败`（全是 16:07–17:40 那场事故的历史行）。旧行会一直赖在窗口里 →
每轮都命中 → 几天内就被无视 = 告警疲劳。

**实际实现**：`tools/log_watch.py` —— **按字节游标只认新增行**，游标落盘；
另加 health_check 没有的两个维度：**心跳停摆**与**进程/状态文件停更**。

| 检测维度 | 判据 |
|---|---|
| 新增故障行 | 关键字表（`BrowserContext` / `重开失败` / `开页异常` / `轮询异常` / `熔断` / `对账闸门` / `结论=不一致` / `Traceback` / `重建失败` / `重建浏览器失败` / `浏览器自动重启失败`） |
| 心跳停摆 | 最后一条心跳超过 **10 分钟** → 告警 |
| 进程消失 | `/proc` 里找不到 `dryrun_bot2.py` → 告警 |
| 状态停更 | `state.json` 超过 **10 分钟**未更新 → 告警 |
| 防轰炸 | 同类告警 **30 分钟冷却** |
| 日志轮转 | 文件变小（copytruncate）→ 游标自动归零 |

**关键字是"挑出来"的，不是随手写的**（都基于实测频率）：
- **不收** `页面不存在/已关闭，正在重新打开…`：单标签页被关后重开成功是小事，
  真出事会由下一行的 `重开失败` 暴露（事故里两行成对出现）
- **不收** 泛指的 `差异`：影子模式下「纸面有仓、交易所无仓」本来就记为"差异"且属预期
  （实测启动时打 `差异 6 条 ｜ 结论=一致`）→ 只收 `结论=不一致`
- 实测 `[对账]` 只在启动/指令时打，**近 1 小时 0 条**，不会周期性刷屏

**部署物**（仓库 `deploy/`）：`signalbot-watch.service` + `signalbot-watch.timer`（每 5 分钟）
+ `install-watch.sh`（幂等安装/卸载）+ `logrotate-signal-bot`（**尚未安装，等用户确认**）

### B1 —— 浏览器上下文死亡后无法自愈（最高优先级）

**真实事故证据**
```

   ⋯ 心跳一直打「运行中 | 持仓 6 笔」       ← 看起来正常，实际完全读不到任何群
17:40:15  重启机器人 → 恢复
```

**后果**：机器人"瞎"了 **93 分钟**，期间四个群的消息**全部漏掉**；
用户 16:37 发的「只开btc和doge」、17:10 发的「持仓情况」「帮助」**根本没被读到** →
用户感知为"机器人指令没反应"。

**根因**：~~整个 `BrowserContext` 死亡。上一轮加的"页面重开失败继续重试"
**只覆盖标签页被关，覆盖不了上下文整体死亡** —— `ctx.new_page()` 必然失败。~~

> ⚠️ **本节根因已于 2026-09-15 晚修正，见上面第 0.1 节**：

（已实现，见第 0.2 节，`--selftest-b1` 全通过，**待生产重启验证**）

**旁证**：~~内核日志**无 OOM 记录**，不是内存问题，更像 Chromium 自身崩溃。~~
→ **已修正**：确实无 OOM（本次用 `sudo dmesg`/`journalctl` 复核确认），但也不是 Chromium 崩溃，

### B2 —— 失联看门狗阈值太长 + 检测维度不够

## 三、相关设计原则（改代码时必须遵守）

1. **绝不猜价** —— 读不准就询问用户，不自动开单
2. **绝不静默丢弃** —— 任何解析失败/未识别信号都要留日志并通知
3. **默认不碰真钱** —— `binance_exec.LIVE[0] = False` 是默认值
4. **一切可核验** —— 金额、点位、成交、盈亏都要能从交易所流水/日志复核
5. **保命机制先挂后撤** —— 改止损必须"先挂新 → 确认成功 → 才撤旧"
6. **订单开之前必须经用户审批**（09-15 新增）
